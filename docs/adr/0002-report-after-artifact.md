# 0002. 報告は pr-review-fix の最後に 1 回だけ送り、PR は Draft で作る

- ステータス: 承認
- 日付: 2026-11-15

## 文脈

- PR は `/pr-review-fix` スキルで作っている。流れは 1 確認、2 PR 作成、3 レビュー、4 修正、5 CI、6 変更の説明を Artifact にする、7 報告
- 手順 6 の Artifact には、背景、設計判断、レビューと修正の経緯まで載る。カードより詳しく、判断のときに読みたい
- 設計書の最初の案は、CLAUDE.md に「PR を作ったら報告する」と書くものだった
- スキルは PR を Draft にせずに作っている

## 検討した選択肢

送る時機

1. 手順 6 のあと、手順 7 の報告の前に 1 回だけ送る
2. 手順 2 で「準備中」として送り、手順 6 のあとに上書きする
3. CLAUDE.md に書き、PR を作った直後に 1 回送る

Draft

- A. 手順 2 で Draft として作り、ダッシュボードの「レビュー依頼」で Ready にする
- B. Draft にせずに作り、「レビュー依頼」はレビュアーの指定だけにする

## 決定

1 と A にする。

- スキルの手順 7 に、報告の前にダッシュボードへ送る手順を足す。CLAUDE.md には書かない
- 送る JSON に `artifact_url`(手順 6 で作った Artifact の URL)を足す。カードの「変更説明を開く」で開く
- テストの結果には CI の結果も入れる
- 既存の PR を直して Artifact を更新したときも、もう一度送って上書きする
- 手順 2 の `gh pr create` に `--draft` を付ける。「レビュー依頼」で `gh pr ready` とレビュアーの指定を行う

## 理由

- 1 なら、カードが出た時点でセルフレビューと修正が終わり、CI も通り、Artifact もある。判断に要るものが揃ってから出る
- 2 は作業中の PR も見えるが、状態が 1 つ増え、準備中のカードで判断しないよう画面で分ける必要がある
- 3 では手順 2 の直後に送られ、レビュー前の要約と CI 前のテスト結果が届く
- A なら、判断する前や修正の途中に、レビュアーへ通知が届かない。CODEOWNERS による自動の依頼も Draft の間は出ない

## 受け入れたトレードオフ

- カードが出るのは CI が通ってから。作業中の PR は画面に出ない
- GitHub 上ですぐマージしたいときも、先に Ready にする手間が 1 つ増える
- Draft を CI の対象から外しているリポジトリでは手順 5 が進まない。使う前に確かめる
- Artifact は非公開なので、URL を開けるのは自分だけ。レビュアー向けの説明は PR 本文に書く

## 再検討する条件

- CI が長くなり、カードが出るまでの遅れが気になったとき
- pr-review-fix を使わずに PR を作ることが増えたとき
