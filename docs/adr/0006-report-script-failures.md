# 0006. 送信スクリプトは送る前にサーバーと同じ検証をし、届かなかったと分かるときだけ inbox に置く

- ステータス: 承認(Python 3.13 以上に頼る部分は 0019 で置き換え)
- 日付: 2026-11-15

## 文脈

- pr-review-fix の手順 7 で、Claude Code が `scripts/report-pr.sh` に判断材料を渡す(0002)
- ダッシュボードが止まっていれば inbox に置き、次の起動で取り込む(0001)
- 送信に失敗したときの扱いを決めないと、次のことが起きる
  - 検証に通らない報告を inbox に置くと、取り込みで断られ続け、カードが出ない
  - サーバーが保存したあとに応答が遅れただけで inbox にも置くと、次の起動で古い報告として上書きし、差し戻しの判断を戻す
  - 環境の問題(道具がない、Python が古い)を判断材料の誤りとして返すと、Claude が直す場所を間違える

## 検討した選択肢

1. 送る前にサーバーと同じ検証をし、届かなかったと分かるとき(つながらない、名前が引けない)だけ inbox に置く。ほかの失敗は理由を出して終える
2. curl が失敗したら一律に inbox に置く(設計書の最初の案)
3. inbox をやめ、届かなければ失敗として終える

## 決定

1 にする。

- 検証は `python3 -I server.py --check` で行い、サーバーと同じ `parse_body` を使う
- inbox に置くのは curl の終了コードが 6 か 7 のときだけ。ほかの失敗は「届いたか分からない」として終える
- 終わり方は 0 が送ったか inbox に置いた、1 が理由を出して失敗、2 が使い方の誤り
- 最初に `gh`、`jq`、`curl`、`python3`(3.13 以上)があるかを確かめ、ないときはそう言って 1 で終える
- 応答の `saved` が `false`(もっと新しい報告がある)ときは、置き換えなかったと知らせて 0 で終える

## 理由

- 検証をサーバーと同じ関数にすれば、オフラインのときに取り込めない報告を inbox に置かずに済み、規則がずれない
- 届かなかったと分かるときだけ inbox に置けば、同じ報告がサーバーと inbox の両方に残らない
- 2 は、保存したあとに応答が遅れたときに判断を戻すおそれがある
- 3 は、ダッシュボードを起動し忘れた日の報告が失われる

## 受け入れたトレードオフ

- 送信スクリプトが Python 3.13 以上に頼る。サーバーと同じ版なので、ダッシュボードを動かせる環境なら足りる
- 「届いたか分からない」ときは Claude が送り直す必要がある。送り直しは上書きなので害はない

## 再検討する条件

- ダッシュボードをほかの PC やサーバーで動かすようにしたとき
