# 0003. サーバーは Host、Origin、Content-Type を確かめ、ほかのサイトからの要求を断る

- ステータス: 提案
- 日付: 2026-11-15

## 文脈

- サーバーは `127.0.0.1:8787` だけで待ち受けるので、ほかの端末からは届かない(0001)
- それでも、同じ PC のブラウザで開いたほかのサイトは `127.0.0.1:8787` へ要求を送れる。本文が `text/plain` の POST なら、ブラウザは事前の確認(preflight)をせずに送る
- フェーズ 3 で、サーバーは自分の GitHub の権限でレビュー依頼やコメントを実行する。ほかのサイトから届いた要求でこれが動くと、勝手に PR を操作される
- DNS rebinding を使うと、ほかのサイトが一覧の API の中身を読める

## 検討した選択肢

1. Host、Origin、Content-Type を確かめる
2. 起動ごとに秘密の値を作り、画面と送信スクリプトに要求のたびに付けさせる
3. 何もしない(127.0.0.1 で待ち受けるだけ)

## 決定

1 にする。

- Host が `127.0.0.1:8787` か `localhost:8787` でない要求は、すべて 403 で断る
- Origin が付いていて `http://127.0.0.1:8787` か `http://localhost:8787` でない要求も 403 で断る。送信スクリプトの `curl` は Origin を付けず、画面からの要求は同じオリジンなので通る
- POST の本文は `application/json` だけ受け付け、ほかは 415 で断る。ほかのサイトが `application/json` で送ると preflight になり、サーバーは CORS の許可を返さないので、ブラウザが止める
- 本文は 64 KiB までにする
- 画面には Content-Security-Policy を付け、ほかのサイトの枠(iframe)に入れさせない

## 理由

- Host を確かめると DNS rebinding を、Origin と Content-Type を確かめると CSRF を防げる。どれも数行で済み、画面と送信スクリプトは何も変えなくてよい
- 2 はより強いが、秘密の値を画面に渡す方法と、送信スクリプトが読む置き場が要る。1 人で手元で使う道具には重い
- 3 では、ほかのサイトを開いただけで PR を操作されうる

## 受け入れたトレードオフ

- 同じ PC で動くほかのプログラムからの要求は防げない。そのプログラムは `gh` も直接使える
- 画面の JavaScript は 1 ファイルに書くので、CSP で `'unsafe-inline'` を許す。画面に出す文字はすべて `textContent` で入れ、HTML として解釈させない

## 再検討する条件

- スマホから見るなど、手元の PC の外から使うようにしたとき
